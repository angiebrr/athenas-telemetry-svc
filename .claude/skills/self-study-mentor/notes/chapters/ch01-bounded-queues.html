Bounded Queues and Worker Pools

Today the handler writes each reading to the store before it answers. This chapter is about putting a fixed-size queue between the two, so the answer goes back as soon as the reading is in memory, and about everything that one change makes you decide.

§1What changes

Moving one arrow is the whole change. Today the 202 is sent after the store write finishes. With a queue, it is sent after the reading is placed in memory, and a separate goroutine does the write later.

That move creates four questions that the synchronous version never had to answer:

  1. What does the client know when it gets a 202? Settled: the reading is in memory, nothing more.
  2. What happens when the queue has no room? Settled: shed with 503.
  3. If more than one goroutine takes from the queue, can one device's readings get reordered? Open. Section 5.
  4. What happens to readings still in the queue when the process is told to stop? Section 6.

§2The vocabulary

The charter calls this an “unbuffered memory dispatch ring”. That phrase isn't standard, and it contradicts itself, because a ring buffer is a buffer. Use the standard terms in interviews:

TermMeaning here
Producer / consumer queueThe overall pattern. Handlers produce readings; workers consume them.
Bounded queueA queue with a fixed capacity. The bound is what makes overload visible instead of turning it into memory growth.
Ring bufferOne way to store a bounded queue: a fixed array whose read and write positions wrap around. A buffered Go channel is one.
Worker poolA fixed number of goroutines taking from the queue. The count limits how many store writes run at once.
BackpressureSlowing the producer down when the consumer can't keep up. Blocking the handler is backpressure.
Load sheddingRefusing work you can't handle, quickly and on purpose. Your 503 is load shedding.
DrainOn shutdown, finishing what's already queued before exiting.
At-most-onceEach accepted reading is written once or not at all. A crash loses whatever is queued.

It's also worth knowing the actor model as a way to look at this. Each worker is a goroutine draining a mailbox. That framing is useful for “who owns this state?” questions. Don't adopt an actor framework, though; building the mailbox by hand is what this milestone is for.

§3What a ring buffer is

A ring buffer is a fixed array plus two positions: where the next item will be written, and where the next item will be read. Both only move forward. When either reaches the end of the array it wraps back to slot 0, so the array is reused forever with no allocation after it is created.

A buffered Go channel is a ring buffer

Inside the runtime, a channel is a struct called hchan. It holds a fixed array (buf), a write position (sendx), a read position (recvx), a count (qcount), two lists of goroutines waiting to send or receive, and a lock. So make(chan T, 8) is exactly Fig 1.2's top row, protected by a mutex. You don't need to build the ring yourself; you need to decide what surrounds it.

An unbuffered channel (capacity 0) is the bottom row. With unbuffered channels and a pool of N workers, your queue capacity is effectively “however many workers are idle right now”. This is why the charter's “unbuffered” and “ring” can't both be meant literally.

Who does this in production

  • The Go scheduler itself. Each processor (P) keeps a local run queue of goroutines: a 256-slot ring buffer. When it fills, half of it spills to a global queue. That's a fourth full-queue policy, “overflow to somewhere slower”.
  • LMAX Disruptor. A ring buffer that avoids locks by giving each slot a sequence number, and pads fields to whole cache lines so producer and consumer counters never share one. The “Read first” paper.
  • Kafka's producer client. Buffers records in memory before sending. When buffer.memory is full, send() blocks for up to max.block.ms, then fails. That's block-then-shed.

§4Accept, shed, or reject

Every request now leaves the handler by one of three routes. The order of the two checks is a design decision: validation comes first, so a malformed reading never takes up a slot that a good one could have used.

The offer never waits

“Slot free?” has to be a check that answers immediately. If the put waits for room, you've chosen blocking, not shedding, and a burst turns into handler goroutines piling up behind a full queue. Go has a direct way to say “try to send, and if you can't right now, do something else”. It's one of the select forms in Learn Go with Tests.

Pseudocode, behaviour only

offer(reading):
    if a slot is free right now:
        put reading in it
        return accepted
    return full                // never wait for room

Why 503 and not 429

429 Too Many Requests says “you are over your limit”. A full queue says the whole server is overloaded, whoever is calling. That's 503 Service Unavailable. Retry-After tells a well-behaved client when to try again. Pick a value now and measure it in phase 3. Per-client limits, and so 429, arrive at M6 with Redis.

What this does to error classification

Until now every error from Ingest was the caller's fault. A full queue is the first that's the server's fault, and the first worth retrying. The HTTP driver and the Spec have to tell the two apart from something sturdier than the message text. That's the open “Spec matches on error prose” debt, now due.

§5Workers and ordering

One worker draining the queue writes readings in exactly the order they arrived, but it caps throughput at one store write at a time. More workers raise that cap, and give up ordering: two readings from the same device can be taken by different workers and finish in either order.

your decision How many workers, and does order matter?

Four defensible answers. Pick one and record why in the Decision Record before you write the first test.

OptionGainsCosts
One workerOrder kept with no extra design. Simplest shutdown.One store write at a time. Fine for a map; a real ceiling once the store is a network call.
N workers, one shared queueBest use of workers; nobody sits idle while there's work.One device's readings can be stored out of order (Fig 1.4, left).
N workers, one queue each, chosen by deviceOrder kept per device, parallel across devices.A very busy device fills its own queue while others sit empty: a hot partition. Shedding becomes per queue.
Don't keep order; sort on readEvery reading carries a timestamp, so the query can sort.Moves the cost to every read, and assumes device clocks are trustworthy.

Questions that settle it: does the Spec, or any client, depend on readings coming back in send order? Does the timestamp already carry the order that matters? What would you say if asked which option survives the store becoming SQS?

Where this shows up again

The right-hand side of Fig 1.4 is a Kafka topic. The hash picks a partition, each partition has one consumer in a group, and ordering is guaranteed only within a partition. Whatever you choose here, you'll meet the same choice at M5 with Kafka's names on it.

§6Ownership and shutdown

A buffer holds readings the client was told are accepted. Restarting the process without draining it loses them, and deploys restart processes far more often than crashes do. So shutdown isn't polish to add later; it's part of the queue.

Rules of channel ownership

ActionWhat Go doesWhat it means for the design
Send on a closed channelPanicsSenders (handlers) must never be able to send after close. So senders can't be the ones who close.
Close a closed channelPanicsExactly one owner closes, exactly once.
Receive from a closed channelReturns remaining items, then the zero value and ok == falseWorkers can drain everything left after close.
range over a channelEnds when the channel is closed and emptyA worker loop written this way drains by itself.

The owner is whoever starts the queue. In this repo that points at main, the composition root, which already builds everything else.

Pseudocode, behaviour only

on stop signal:
    stop accepting connections; wait for in-flight requests   // no more senders exist after this
    close the queue                                            // only the owner, only once
    wait until every worker has finished draining, or a deadline passes
    exit

each worker:
    for every reading taken from the queue, until it is closed and empty:
        write it to the store
    report done

Things this needs that the repo doesn't have yet

  • Signal handling. main doesn't listen for SIGTERM today. The standard library has a helper that turns a signal into a cancelled context; it's covered alongside Context in Learn Go with Tests.
  • A server you can stop. gin's Run starts a server you can't shut down cleanly. A plain net/http Server with the gin engine as its handler has a Shutdown method that does the first step of Fig 1.5.
  • A deadline. Kubernetes waits 30 seconds by default after SIGTERM before it kills the pod. A drain that takes longer is cut off, and whatever is left is lost. Choosing the deadline is choosing your loss window.

What this still doesn't protect against

A crash, an out-of-memory kill, or SIGKILL loses everything in the queue. That's the at-most-once trade you accepted on purpose. Be ready to say it first in an audit, and to name the fix: M4's transactional outbox makes the write durable before the 202.

§7What capacity buys

A buffer buys time, not throughput. If readings arrive faster than workers can write them for long enough, any finite queue fills. Capacity only sets how long a burst can last before you start shedding.

Little's Law

L = λW: the average number of items in a system equals the arrival rate times the average time each spends there. At 100,000 readings a second with each waiting 2 ms in the queue, about 200 are queued on average. That gives you a starting point from two numbers you can measure, and it's why capacity is a phase 3 decision. You'll have the measurements then.

Watch the opposite failure too. An unbounded queue never sheds, so the same burst becomes growing memory and growing wait times, and ends in an out-of-memory kill that loses everything queued. A bound turns that slow failure into a fast, visible one.

How it gets asked

  • “What happens when your consumer is slower than your producer?” That's the backpressure question; the answer is §4 and §7.
  • “Your service returned 202. What can still be lost?” That's §6.
  • “How did you size the buffer?” Little's Law, from measurements, not a round number.
  • “Who closes the channel?” The single owner, after every sender is gone.
