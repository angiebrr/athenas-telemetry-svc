Testing Outside-In: The Shape of This Suite

Every test in this repo answers one of two questions: what does the system promise, or does this one piece keep its part of the bargain? This chapter names the kinds of test you have, what each one can see, and the decisions from M1 that gave the suite its shape.

§1Two axes, not one

Most people fumble testing vocabulary because they use one word for two different properties. Keep them apart:

AxisValuesThe question it answers
LevelAcceptance (end-to-end) · integration · unitHow much of the real system is running when the test executes? (GOOS ch. 1)
ReuseContract test · single-subject testIs the test body written once and run against many implementations, or written for one?
IsolationSolitary · sociableDoes the unit under test get real collaborators (sociable) or doubles (solitary)? (Fowler)

The key idea for this repo: the body doesn't determine the level, the entry point does. TelemetrySpec is one body. Bound to telemetry.Service it is a fast, in-process test. Bound to the HTTP driver and a container it is an end-to-end test. Same assertions, different evidence.

§2The kinds of test here

There are two kinds of artifact. Shared test bodies take a subject and assert against it; go test never runs them directly. Entry points (TestXxx) bind a concrete subject and call a body, or assert directly.

Two kinds of contract

TelemetrySpec and StorerContract are both shared bodies, and both are called “spec” or “contract” loosely. They sit on opposite sides of the hexagon:

  • TelemetrySpec is a contract on a driving port. It describes what a caller of the service gets. It is the system's promise to the outside world, and it is the Spec that new behaviour starts from.
  • StorerContract is a contract on a driven port. It describes what the service requires of any storage adapter. Nothing outside the service ever sees it. Its job is to make adapters substitutable.

(The question bank once called the storage body data.DataStoreSpec. It's StorerContract now, in a _test.go file, because only this module's tests need it.)

§3Doubles: the five names

Gerard Meszaros's vocabulary, which Fowler popularised. Each one answers a different need:

Why the distinction matters for telemetry.Query. Calling the in-memory store a “mock” implies the test is checking which calls were made. It isn't; it checks the state that comes back. A fake has a different risk from a mock: a fake can drift from the real thing and make every test above it lie. That's the reason StorerContract exists. When Postgres lands, both adapters run the same contract, so the fake can't quietly behave differently from production.

Only mock types you own (GOOS ch. 8). At M3, you'll generate mocks for your own publisher interface, not for the AWS SDK. The SDK gets exercised for real against LocalStack.

§4Spec, driver, and the exported package

The pattern is three pieces. The Spec is the rules, written only against two interfaces. A Driver is the plumbing that satisfies those interfaces against a real system. The entry point wires one to the other. One Spec, many drivers: HTTP today, SQS and multi-pod later, and in-process adapters for speed.

Why specifications is an exported, non-test package

Go doesn't let one module import another module's _test.go files. The acceptance tests live in a separate module, so the Spec has to be ordinary, exported code. The costs:

  • Test-only dependencies (testify, uuid) become part of the service module's import graph. They aren't linked into the binary unless main imports the package, but they show up in go.mod and in vulnerability scans.
  • The Spec is part of the module's public surface. Anyone could import it, so its signature is an API.
  • Helpers it calls, like shared.ValidTelemetry, must be exported too, even though they're test data.

Who else does this. The Go standard library ships conformance suites as normal packages: testing/fstest.TestFS checks any fs.FS implementation, and golang.org/x/net/nettest.TestConn checks any net.Conn. Same shape: the suite is exported so other packages can prove they satisfy an interface.

Why the driver hardcodes /v1/telemetry

The driver is a black-box client. If it imported api.TelemetryPath, renaming the route would rename it in the test as well, and the suite would stay green while every real device broke. A duplicated literal is the point: the test holds the published contract, and the code has to match it.

Why acceptance cases need no reset between runs

Each case creates its own device with a fresh UUID (shared.ValidTelemetry()), so no case can see another's data. This is isolation by unique keys. The alternative, a Reset() method on the interface, would put a test-only operation on a production port. Every future driver (SQS, Postgres, many pods) would need to implement “delete everything”, which is impossible or dangerous against a shared environment. Unique keys also let cases run in parallel and against a long-lived deployment.

§5What each level catches

TelemetrySpec used to run at three levels: domain, httptest, and container. On 2026-09-21 the handler tests switched to hand-written status-code cases, so it runs at two. The question still holds for the three places behaviour can break:

LevelCatchesCan't seeCost per run
Domain (telemetry.Service)Wrong rules: validation, query semantics, eventual visibility.JSON field names, status codes, routing, config, the image.Milliseconds.
Transport (httptest)Binding and serialisation bugs, wrong status codes, an internal error leaking into a response body.The Dockerfile, env-var config, the real listener, the build.Milliseconds.
ContainerA broken image, a missing env var, the wrong port, release-mode differences (APP_ENV=prod), a route the driver can't reach.Edge cases, cheaply. It's too slow to cover them all.Seconds to build and boot; needs Docker.

If the suite got too slow, delete from the middle first. A Spec case that the domain level covers fully, and whose transport translation a handler test covers, doesn't need a container round-trip too. Keep at least one container case per route as a smoke test. The risk you accept: an interaction between layers that only shows up when they run together. Don't delete the domain level; it's what makes the Spec fast enough to run on every save.

Why seven validation cases, but one Spec case

The Spec states a promise: invalid telemetry is rejected. One case proves the validation is wired in end to end. Which fields count as invalid is a rule that lives in one function, so it's tested exhaustively there, at unit speed. Running all seven through a container would multiply the slowest tests by seven to prove nothing new about the wiring.

The ice-cream cone

The test pyramid has many fast unit tests at the bottom and few end-to-end tests at the top. The ice-cream cone is that shape inverted: most coverage lives in slow, flaky end-to-end tests, often with manual testing on top. It forms when every new behaviour gets a container case “to be safe”. In this repo the risk is M3–M5: LocalStack, Postgres, and Kafka containers will make the acceptance suite slow enough that people stop running it. Each milestone should add more unit coverage than end-to-end coverage.

§6Outside-in and the walking skeleton

A walking skeleton (GOOS ch. 4) is the thinnest slice of real functionality that can be built, deployed, and tested end to end. You build it before any feature because the hardest problems in a new system are usually in the plumbing: the build, packaging, configuration, and how the test reaches the system. A skeleton surfaces them on day one, when they're cheap to fix, and gives every later feature a place to plug in its acceptance test.

Outside-in means starting from a failing acceptance test that describes behaviour a caller can see, then working inward, discovering each collaborator's interface because the layer above needs it. Inside-out builds the pieces first and assembles them later.

What goes wrong if you build the store first: you have to guess its interface before anyone needs it, and guesses tend to be too general (methods nobody calls) or wrong (the query the handler actually needs isn't there). You also have nothing externally observable to test. This repo has a concrete version of the argument: on 2026-08-26, M2 was reordered to build the store and the GET endpoint before the dispatch ring, because a ring with no destination has no behaviour an acceptance test can drive.

§7Red for the right reason

A new test should fail because the behaviour is missing, with a message that says so. It shouldn't fail because it doesn't compile, because setup is broken, or because some other rule fires first. A test that fails for the wrong reason will often pass for the wrong reason too, once you “fix” it.

  • From this repo, failing for the wrong reason: the port cases in TestAppConfigValidate once failed on an empty Env field, not on the port value they were about. The fix (2026-09-26) built each case from a valid config and changed only the field under test.
  • From this repo, passing for the wrong reason: M2's first engine test (“queued readings eventually reach the store”) is satisfied by a plain synchronous Insert. Green, but it didn't force the design it was written for. That's why the next tests are “Push returns while the store is blocked” and “a full queue rejects”.
  • How to notice: read the failure message before writing any code. Ask “what is the smallest wrong implementation that passes this?” If a trivial one passes, the test isn't constraining what you think it is.

§8Listening to the tests

GOOS ch. 20: when a test is awkward to write, the awkwardness is usually telling you something about the design. The response is to change the design, not to force the test.

This repo's example: the config seam (2026-09-26). The defaults-setup function was injectable so a test could replace it. An injected double then hid a real bug: production defaults were being set on viper's global instance rather than the one being read, so every env var was silently ignored, and the test stayed green. The fix was to make the function non-injectable and have tests exercise the real defaults. The lesson: an injectable seam can let a test replace the very code it was meant to check.

The same instinct shaped the full-queue test for M2 (2026-11-05): a hook inside the engine that “pretends to be full” was rejected for the same reason, and a blocking store stub was used instead, so the real engine runs.

§9M1's structural decisions

Why Validate isn't a method on models.Telemetry

models is exported and imported by the acceptance module. If validation lived on the model, a driver could call it client-side and return the error without ever contacting the server. The Spec would pass while the server validated nothing. Putting Validate in internal/telemetry means only the service can run it, so a passing Spec proves the server rejected the input.

Why a replace directive and no go.work

The project notes say “Go workspaces”, but the repo has two modules joined by replace github.com/angiebrr/athenas-telemetry-svc => ../athenas-telemetry-svc in the acceptance module's go.mod. That makes the acceptance tests always build against the local working tree, not a published version, with no extra file for developers or CI to keep in sync. A go.work would do much the same locally, but it's usually kept out of version control, and then CI wouldn't use it.

The dependency flows one way: acceptance tests import the service; the service never imports the tests. A cycle would make the tests part of the thing they test, and the service would carry test code into its build.

What the container test proves that httptest doesn't

That the artifact you'd ship actually works: the Dockerfile builds from the repo root, the binary starts, it reads PORT and APP_ENV from the environment, it listens where you think it does, and it runs in release mode. httptest calls the gin engine in-process and skips all of that. The cost is seconds per run and a Docker dependency, and if Docker isn't running the suite now fails rather than silently skipping.
