Metrics, Logs, and Cardinality

The planned stack is Prometheus for metrics, Loki for logs, and Grafana on top. Both stores are cheap for the same reason: they index very little. This chapter is about what that means for the labels you choose, which signals tell you the queue is in trouble, and how to alert on shedding without waking someone for nothing.

§1What a time series is

In Prometheus, a series is one metric name plus one exact set of label values. So http_requests_total{route="/v1/telemetry", code="202"} and the same metric with code="503" are two series. Each series is stored and indexed separately, and recent samples for every active series are held in memory (the head block).

Cardinality is the number of series. It's roughly the product of the number of distinct values of each label: 3 routes × 6 status codes × 4 pods = 72 series. That's cheap. Cost scales with series count, not with how many requests you serve.

§2Cardinality, and device_id

Add a device_id label and every device becomes its own series, multiplied by every other label. A million devices on one metric with 72 combinations is 72 million series. What grows:

  • Memory in the Prometheus server, for each active series in the head block.
  • The index, and the time to query it.
  • Churn: devices come and go, so old series go stale and new ones are created constantly. Short-lived series are especially expensive. An SSRC (Chapter S2), which is random per media stream, is the extreme version.

The result is a Prometheus server that runs out of memory or a vendor bill that scales with your device count. Where device_id can live instead: in log lines (not labels), in traces, in a store built for high-cardinality data (a columnar analytics database), or in Athenas itself, which is literally a per-device store. Metrics answer “how is the fleet doing?”; per-device questions go elsewhere.

The same mistake can happen by accident with HTTP routes: label by c.FullPath(), the route template (/v1/telemetry/:device_id), never the raw URL, which contains the ID.

§3How Loki indexes

Loki indexes only the labels on a log stream, not the text of the log lines. Each unique label set is a stream. Lines are compressed into chunks per stream. A query first uses the label index to pick streams, then scans those chunks by brute force (with filters such as |= "error" or a | logfmt parser).

Loki (labels only)Full-text index (Elasticsearch-style)
Ingest and storage costLow. The index is small; chunks compress well and sit in object storage.High. The index can be as large as the data.
Query speedFast when labels narrow it down; slow for “search everything for this string”.Fast for arbitrary term search.
Label choiceCritical. Few, low-cardinality labels.Less critical.

This changes how you pick labels. A high-cardinality label (device_id) creates a stream per device, and many tiny streams mean many tiny chunks and a bloated index, the same failure as in Prometheus. Use labels for things you'd select by (service, environment, level), keep the device ID in the line, and filter on it at query time. (Recent Loki versions also offer structured metadata for attaching high-cardinality fields to lines without indexing them.)

§4RED and USE

MethodSignalsForIn Athenas
RED (Tom Wilkie)Rate, Errors, DurationRequest-driven services: things that receive requests.The HTTP handlers: requests per second, 4xx/5xx rate, latency histogram, per route.
USE (Brendan Gregg)Utilization, Saturation, ErrorsResources: things with capacity.The queue and the worker pool.

For the ring specifically:

  • Utilization: fraction of time workers are busy writing.
  • Saturation: queue depth relative to capacity. This is the early warning: depth rising toward capacity means shedding is coming. Time-in-queue (staleness) is the same signal measured in seconds.
  • Errors: shed count, and later, failed writes.

§5Histograms, summaries, and p99

A summary computes quantiles (such as p99) inside each process and exports them as finished numbers. A histogram exports counts per bucket (requests that took ≤ 5 ms, ≤ 10 ms, …) and the quantile is computed at query time with histogram_quantile.

You can't average p99s across pods. A percentile isn't a linear quantity. If pod A handled 1,000 requests with a p99 of 10 ms and pod B handled 10 requests with a p99 of 2 s, the average of the two p99s (about 1 s) describes nobody's experience. The true fleet p99 depends on the full distributions. Histogram buckets are additive: sum the bucket counts across pods, then compute the quantile from the combined distribution.

Choose histograms for request latency in a multi-instance service. The costs: the quantile is an estimate whose accuracy depends on the bucket boundaries, and each bucket is a series. Summaries are only reasonable when you'll never aggregate across instances. Newer Prometheus versions add native histograms, which pick bucket boundaries automatically and reduce the bucket-choice problem.

§6Alerting on shedding

The metric: a counter of shed requests next to a counter of accepted ones. The signal is the ratio, shed ÷ (shed + accepted), over a window, because an absolute count means nothing without traffic volume.

When to wake someone: a page should mean that users are being hurt now, and that a human needs to act. A burst that sheds for a few seconds and recovers is the system working as designed, so that's a dashboard item. Page on sustained shedding that burns through an error budget. For example, with an SLO of 99.9% of readings accepted, the SRE Workbook's multiwindow approach pages when the budget is burning fast in both a long window (1 hour) and a short one (5 minutes). The long window proves it's real; the short one proves it's still happening. Slow burns become tickets.

The early warning is saturation (§4): queue depth climbing toward capacity before any shedding starts. That belongs on the dashboard, and maybe a ticket, not a page.

§7Why /metrics gets its own port

  • Exposure. Metrics reveal internals: route names, error rates, queue sizes, version labels. Keep them off the public listener; only the scraper needs them.
  • Independence under overload. When the main listener is saturated or shedding, you need metrics most. A separate listener isn't stuck behind the same queue, and it isn't affected by public-traffic middleware.
  • Clean RED numbers. Scrapes on the main port would be counted as requests by your own metrics middleware.
  • Different policy. Auth, network policy, and firewall rules can differ per port.

The port number: avoid 9090, which is the Prometheus server's own default and will collide in a compose file. 2112 is a common convention for application metrics.
