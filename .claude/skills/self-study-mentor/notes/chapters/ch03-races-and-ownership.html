Shared Memory, Races, and Ownership

The store is a map that many goroutines touch. This chapter is about how you know that's safe, what the race detector can and can't tell you, why a returned slice is a hole in a mutex, and when one goroutine owning the state beats a lock.

§1Three ways concurrent code goes wrong

“Thread-safe” hides several different failures. Name them separately, because different tools catch each one.

FailureWhat happensWhat catches it
Data raceTwo goroutines access the same memory, at least one writes, and nothing orders the accesses (no lock, channel, or atomic). In Go, a race on a map can crash the process outright (“concurrent map writes”).-race, when the racing accesses actually happen during the run.
Atomicity violation (race condition)Each access is properly locked, but a multi-step operation isn't. Example: “check whether the device exists” and “insert” as two separate locked calls; another goroutine acts in between.Not -race: every access is synchronized. Design review, and tests that force the interleaving.
Aliasing (escaped state)The lock is held correctly inside the method, but a reference to the guarded data leaves it. The caller then reads or writes it without the lock.A contract test that mutates what it got back and checks the store didn't change. -race only if a concurrent writer happens to overlap.
DeadlockGoroutines wait on each other forever.The runtime only if every goroutine is blocked (“all goroutines are asleep”). A partial deadlock shows up as a test timeout.

Note the vocabulary: a data race is a precise memory-model term. A race condition is the broader idea that the outcome depends on timing. You can have a race condition with no data race.

§2What -race proves

Go's race detector is built on ThreadSanitizer. It instruments every memory access and tracks happens-before relationships created by locks, channels, and sync primitives. When two accesses to the same address aren't ordered by happens-before and one is a write, it reports a race with both stack traces.

  • It's dynamic. It only sees code paths that actually execute during this run, and only interleavings that actually occur. A race in an untested path, or one that needs a timing your test never produces, goes unreported. A clean run is evidence, not proof.
  • It has no false positives in practice. If it reports a race, there is one. Fix it; don't argue with it.
  • It doesn't see logic. Atomicity violations, aliasing that never overlaps a writer in the test, deadlocks, and wrong results are all invisible to it.
  • It's expensive. The Go docs give typical overhead as 5–10× memory and 2–20× execution time. That's why it runs in CI and in a dedicated mise run test telemetry-svc --race, not in production.

So -race needs tests that actually run goroutines concurrently against the shared state. A race-clean suite of single-goroutine tests proves almost nothing about concurrency.

§3The slice that escapes the lock

A Go slice is a small header: a pointer to a backing array, a length, and a capacity. Returning a slice copies the header, not the array. If GetByDeviceID returned the slice stored in the map, the caller and the store would share one backing array.

The mutex protects the critical section. Once the method returns and unlocks, nothing stops Insert from appending into spare capacity in the same array, or a caller from writing into it. That is a data race the lock can't see, because one side never takes the lock.

Why slices.Clone isn't enough. It copies the outer slice of Telemetry values, but each value contains Metrics, which is itself a slice header pointing at a shared array. A shallow clone still leaks every record's metrics. The store therefore deep-copies: a new outer slice, and a cloned Metrics per record. The StorerContract leak case mutates both DeviceID and a Metrics element on what it got back, so a regression to a shallow clone fails a test.

The general rule: a lock protects data only if no reference to that data leaves the lock. Copy on the way out, or hand out immutable values.

§4How you know the store is safe

Three kinds of evidence, each covering a different failure from §1:

  1. By construction. Every access to the map happens with the mutex held, and nothing that points into the map is returned. You can check this by reading two methods.
  2. By the race detector. Tests that hammer the store from many goroutines, run with -race, catch data races that actually occur.
  3. By the contract. The leak case catches aliasing deterministically, no timing luck needed, and it will run against Postgres at M4 too.

Two failures, two tools, which is the shape of a good answer: data races are caught by -race; escaped references are caught by a deterministic mutation test.

§5Mutex or owning goroutine

Go's proverb is “don't communicate by sharing memory; share memory by communicating.” The alternative to a mutex is a single goroutine that owns the map. Everyone else sends it requests over a channel and gets answers back. This is the actor or monitor goroutine pattern, and it applies the single-writer principle: only one goroutine ever touches the state, so no lock is needed.

MutexOwning goroutine
CodeA few lines. Easy to read.A request type, a reply channel, a loop, a shutdown path.
Cost per operationUncontended lock: tens of nanoseconds.Two channel operations and a goroutine switch: noticeably more.
Concurrency of readsCan use RWMutex to allow parallel readers.Fully serialized.
Multi-step invariantsEasy to get wrong (§1, atomicity).Natural: each request runs to completion alone.
Backpressure and lifecycleNone built in.The mailbox is a queue; its capacity is a backpressure point, and the goroutine has a clear lifecycle.

For a map with insert and lookup, a mutex is the right tool, and the Go wiki says the same: channels for passing ownership and coordinating work, mutexes for guarding a cache or state. When to switch: when operations need invariants that span several steps, when the owner has to do slow work (I/O) in order, or when sharding the state by key lets each owner run without contention (one goroutine per shard). That last one is what per-worker queues would have needed in Chapter 1 §5 to actually remove the store's mutex.

§6Buffered vs. unbuffered under a burst

Chapter 1 §3 showed that an unbuffered channel stores nothing: a send completes only when a receiver takes it. That changes what a burst does to the handler.

ChannelWith a blocking sendWith a non-blocking send (shed when you can't)
UnbufferedEvery request waits for an idle worker. Handler latency includes the wait for a worker, so p99 latency tracks the burst. Goroutines pile up.Every request arriving while all N workers are busy is shed. Even a tiny burst produces 503s.
Buffered (capacity C)Requests return in microseconds until the buffer fills, then wait like unbuffered. Tail latency is low for short bursts and unbounded for long ones.Up to C requests are absorbed instantly; shedding starts only once the buffer is full. Latency stays flat; the cost moves to staleness (time in queue).

A buffer doesn't make work faster. It moves where waiting happens: from the client's request (latency) to the reading's time in the queue (staleness). For a fire-and-forget 202, that's the right place for it. Who closes the channel, and why it can't be the senders, is Chapter 1 §6.
