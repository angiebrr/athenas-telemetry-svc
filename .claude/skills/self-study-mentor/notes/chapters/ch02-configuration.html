Configuration and the Composition Root

Config looks like plumbing, and that's why the interesting bugs live there. This chapter covers where Athenas reads its settings, the test that passed while production ignored them, what the image claims about itself, and what to do with a library that only offers a global switch.

§1Sources and precedence

config.InitEnv builds an AppConfig (PORT, APP_ENV) from three sources. Later sources win:

  1. Defaults, set in code: port 8080, env dev.
  2. A .env file, if one exists. Useful on a laptop.
  3. Environment variables. Authoritative, as 12-factor says they should be.

(This follows viper's own order, which also puts flags and explicit Set calls above the environment. Athenas uses neither.)

A missing .env is a warning, not a failure. The container never has one; it's configured by environment variables. Any other read error, such as a malformed file, is fatal. After reading, AppConfig.Validate checks the values: the port must be between 1024 and 65535 (no privileged ports), and the env must be dev or prod. Failing fast at startup is the point: a bad config should stop the process before it serves anything, not surface as strange behaviour an hour later.

§2The test that couldn't fail

The defaults-setup function was originally injectable, so tests could swap it out. Production's version set its defaults on viper's global instance, while the config was read from a separate instance. The result: every env var was silently ignored in production. The tests stayed green, because they injected their own defaults function, which didn't have the bug. The test had replaced the code it was supposed to be checking.

What changed, so a test can't miss it again:

  • The defaults function became non-injectable. Tests now exercise the real one.
  • A TestConfigInit case sets APP_ENV=prod, which isn't the default. If that value doesn't come through, nothing else could have made the test pass. A test that sets a variable to its default value proves nothing about whether the variable is read.
  • The container suite runs the image with APP_ENV=prod, so the real wiring is exercised end to end.

The general lesson, which Chapter 1 §8 also draws: a seam you add for testing is a place where the test and production can diverge. Put seams where you need to control an input you can't otherwise control, not around code you could just run.

§3Logging config

Logging the parsed config at startup is tempting, because it answers “what was this process actually running with?” The risk is secrets. Today the config is a port and an env name. At M3 it gains AWS credentials or a queue URL; at M4, a Postgres connection string with a password in it. Logs get shipped to Loki or a vendor, retained for weeks, and read by more people than the secrets should be.

Safer options:

  • Log an allowlist of non-secret fields instead of the whole struct.
  • Give secrets a type whose String and LogValue methods print [redacted], so that logging the struct by accident is safe.
  • Log where each value came from (default, file, env) rather than the value itself.

§412-factor, and APP_ENV=prod in the image

Factor III, Config: store config in the environment, so the same code can run in any deploy without changes. Factor V, Build, release, run: the build produces an artifact (the image); a release combines that artifact with one environment's config; then it runs. The image is supposed to be environment-neutral.

The Dockerfile sets APP_ENV=prod. That bends factor V on purpose:

  • Gain: the artifact is safe by default. Anyone who runs it without thinking gets release mode, and the acceptance suite tests the configuration that actually ships.
  • Cost: the image claims to be prod wherever it runs, unless the deploy overrides APP_ENV. A staging deploy that forgets the override is labelled prod.

Why APP_ENV, not ENV: POSIX sh gives ENV a meaning. An interactive shell reads the file named by $ENV at startup. Prefixing the name avoids colliding with the shell.

§5The composition root

The composition root is the one place where the application's object graph is assembled. In Go it's main. In Athenas, main loads config, builds the store, builds the service, maps the environment to a server mode, and builds the server.

“Prod means release mode” lives in main. main translates config.EnvProd into api.ReleaseMode and passes it to api.NewServer as a functional option. As a result:

  • internal/api never learns environment names. It knows about server modes, which is a transport concept.
  • api doesn't import config, so the dependency arrows still point inward.
  • api.ServerMode wraps gin's mode strings, so main never imports gin.
  • A new environment (say staging) changes one if in main, not the HTTP layer.

§6Global switches

gin has no per-engine mode. gin.SetMode writes a package-level value, so it's process-global. The two places to call it, both weighed on 2026-09-28:

WhereExposesHides
In mainThe global side effect is visible where the process is assembled.Nothing, but main has to import gin.
Inside api.NewServer (chosen)gin stays inside one package.A constructor quietly changes process-wide state. Two servers built with different modes, for example in parallel tests, interfere with each other.

The cost of the chosen option should be written where callers will see it: in NewServer's doc comment.

What release mode actually changes: gin's own debug output. In debug mode gin prints every registered route at startup and warns about things like running in debug mode. Release mode turns that off. It doesn't change your middleware, request handling, or meaningful performance.

§7Zero values at a JSON boundary

Every Go type has a zero value, and encoding/json leaves a field at its zero value when the JSON omits it. So a request with no timestamp decodes to Timestamp: 0, and the server can't tell “missing” from “the device really sent 0”. Accepting 0 meant a missing timestamp was silently stored as 1970-01-01.
