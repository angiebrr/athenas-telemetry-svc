Chapter 5 · Milestone 2

Overload, Retries, and What 202 Promises

Chapter 3 built the queue. This chapter is about the contract around it: what the caller has been told, what can still disappear, what overload does under each policy, and what a well-behaved device does when it's refused.

§1What 202 promises

RFC 9110 defines 202 Accepted as: the request has been accepted for processing, but the processing has not been completed, and it may or may not eventually be acted upon. HTTP itself makes no stronger promise. Your Spec's port doc says what yours means: the reading was valid and is queued, it should become queryable, and it could still be lost.

What can still be lost after a 202

  • A crash, panic, out-of-memory kill, or SIGKILL while readings are queued.
  • A deploy whose drain runs past the deadline (Kubernetes' default grace period is 30 s).
  • From M3 on: a write to the destination that fails after acceptance, if retries are exhausted and there's no dead-letter path.

This is at-most-once delivery: each accepted reading is stored once or not at all. The device never retries, because it was told the reading was accepted.

§2Fire-and-forget vs. group commit

On 2026-10-09 you weighed three options. Here they are side by side:

Group commit is a real, named technique: databases use it to share one disk flush among many transactions (Postgres's commit_delay), and a Kafka producer with acks=all and linger.ms does the same thing over the network.

What would make you switch. The reversal conditions you wrote down: telemetry that includes alarm events or other readings that can't be replaced by the next sample, or a measured loss rate that isn't small. (Counters, interestingly, make at-most-once safer: see Chapter S3 §6.)

§3Measuring what you lose

“Some loss is acceptable” is only a decision once it's a number. Three ways to get it, from cheapest to most complete:

  1. Server-side counters. Count readings accepted, written, and shed. At shutdown, record how many were still queued when the deadline hit. Accepted minus written, over time, is the loss the server knows about. It can't count what a crash took, because the counter dies with the process.
  2. Reconciliation. Compare a count from the producer side (devices, or a load generator) with what's in the store for the same window.
  3. Sequence numbers. Each device numbers its readings. A gap in a device's sequence at the destination is a lost reading, whatever caused it, including crashes. This is the end-to-end check from §4.

§4The end-to-end argument

Saltzer, Reed and Clark (1984): a function like “make sure the data arrived intact” can only be completely and correctly implemented with the knowledge and help of the application at the endpoints. Building it into a lower layer can improve performance, but it can't replace the check at the ends. Their example is file transfer: a reliable network doesn't help if the disk at the far end corrupts the file, so the application has to verify a checksum end to end anyway.

Applied to your 202: the queue, the drain, and later SQS all raise the odds that a reading arrives. None of them can guarantee it, because each only knows about its own hop. If a device truly needs to know its data was stored, the evidence has to come from the destination: sequence numbers checked where the data lands, or an acknowledgement sent only after a durable write.

You already used this argument once. In Chapter 3 §5, ordering is stamped at the source (timestamps) and restored at the destination (sort on read), instead of being carried through every hop of the pipeline.

§5Block, shed, or drop

Three policies for a full queue, under sustained overload (arrivals faster than writes for a long time):

PolicyLatencyMemoryWhat the client sees
BlockGrows without bound. Every request waits behind the full queue.Grows: each waiting request holds a goroutine, a connection, and its body.Slow successes, then timeouts. Clients that time out and retry add more load: a cascading failure.
Shed (chosen)Stays low. Refusals are immediate.Bounded by queue capacity.An honest 503 it can act on. The loss is visible at the boundary.
DropStays low.Bounded.A 202 for a reading that is then thrown away. Loss is invisible to the client and, without a counter, to you.

Shedding and fire-and-forget fit together. A shed happens before acceptance, so it doesn't break any promise. Drop breaks the promise silently, which is the worst of the three for a system that claims 202 means accepted.

§6Open systems, and real backpressure

Queueing theory separates two kinds of load:

  • Closed system: a fixed population of clients, each waiting for a response before sending its next request. If the server slows down, arrivals slow down too. Slowness is self-limiting.
  • Open system: arrivals don't depend on how fast you respond. New requests keep coming at their own rate. Devices on a timer are an open system: a thermostat sends every 30 seconds whether or not you answered the last one.

That's why blocking fails for Athenas. In a closed system, blocking is backpressure: it slows the producers. In an open system, blocking only makes the queue of waiting requests longer, because the arrival rate doesn't change. The only way to keep an open system stable under overload is to refuse work.

Is a 503 with Retry-After backpressure?

Mostly it's load shedding, with an advisory hint attached. True backpressure means the producer can't proceed until the consumer is ready: a blocked send, TCP's flow-control window, a pull-based consumer. Retry-After only asks the client to wait. A well-behaved device honours it; a buggy one ignores it, and the server can't make it.

Where you get real backpressure in this project

  • Inside the engine: between workers and the store. A slow store blocks workers, which stop taking from the queue, which fills, which triggers shedding at the edge. Backpressure inside the process turns into shedding at the open boundary.
  • At M5, with Kafka: consumers pull. A consumer that's falling behind pauses its partitions and fetches nothing more until it catches up. That's a closed loop, so it's real backpressure. It works there because Kafka holds the backlog durably on disk, so slowing down costs lag, not data.

The timeout row is the subtle one. A timed-out request may have succeeded, so retrying it can store a reading twice. Retries turn at-most-once into at-least-once, and at-least-once needs either idempotent writes or duplicate tolerance (a natural key such as device ID plus timestamp). This is M3's main topic (Chapter 7 §1).

Exponential backoff with jitter

Exponential backoff doubles the wait after each failure (for example 100 ms, 200 ms, 400 ms, up to a cap), so a struggling server gets progressively more room. Without jitter, clients that failed together retry together: after an outage, a fleet of devices that all reconnected at the same moment retries in synchronized waves, and each wave knocks the server over again. That's a thundering herd. Jitter randomizes each wait (Brooker's “full jitter” picks uniformly between zero and the backoff value), which spreads the retries out so the server sees a smooth rate instead of spikes.

Retry budgets

SRE ch. 22's warning: retries multiply across layers. If three layers each try up to four times, one user request can become 4 × 4 × 4 = 64 requests at the bottom, exactly when the bottom is overloaded. Limit retries per request, retry at one layer only, and cap retries as a fraction of normal traffic.

§8Why buffer in memory at all

At M3 the destination is SQS. Why not have the handler write straight to SQS and return 202 after that?

Handler writes to SQS directlyBuffer in memory, workers write to SQS
Latency per requestIncludes an SQS round trip (tens of milliseconds).Microseconds.
CostSQS bills per request. One message per call is the most expensive way to use it.Workers can batch up to 10 messages per SendMessageBatch call, so roughly a tenth of the requests.
Durability of the 202Durable: the 202 means it's in SQS.At-most-once until it's flushed.
When SQS is slow or downEvery client feels it.The buffer absorbs a blip; then shedding starts.

Production clients buffer in-process anyway. The Kafka producer batches records in memory (batch.size, linger.ms, buffer.memory). The Kinesis Producer Library aggregates records before sending. OpenTelemetry's batch span processor queues spans and exports them in batches. Prometheus remote-write keeps an in-memory queue of samples per shard. Each makes the same trade you made: a small loss window in exchange for latency and cost. M4's transactional outbox is how you'd close that window if it ever matters.
